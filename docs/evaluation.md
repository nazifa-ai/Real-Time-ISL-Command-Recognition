## 1. Evaluation protocol

| item | value |
|---|---|
| dataset | AI4Bharat **INCLUDE-50** (release of pre-extracted MediaPipe keypoints) |
| classes | 50 (frozen from the official metadata, `datasets/metadata/vocabulary.json`) |
| clips used | 958 (the full INCLUDE-50 pool) |
| primary split | `session_disjoint` — train 652 / val 152 / test 154, seed 42 |
| secondary split | `official` — train 686 / val 80 / test 192 (AI4Bharat's own train/test files) |
| input | 30 frames × 225 features (75 landmarks × x,y,z, shoulder-normalised) |
| fairness contract | identical data, split, seed, class mapping, sequence length, augmentation, callbacks and test set for all three models; no test-time augmentation, no per-model tuning |
| metrics | top-1 accuracy, macro/weighted precision/recall/F1, per-class P/R/F1, confusion matrices, parameter count, single-clip latency, throughput |

### Why `session_disjoint` is the primary protocol

AI4Bharat's official train/test files reuse recording sessions across the split:
measured on this dataset, **199 of 299 recording clusters span train and test**
(167 near-duplicate clip pairs), so the official test set is partly seen data. The
official split is *not* signer-disjoint either — INCLUDE publishes no signer ids at
all, so a signer-disjoint evaluation is impossible with this release.

`session_disjoint` therefore pools the full INCLUDE-50 pool and allocates **whole
recording clusters** (clips whose file ids lie within a gap of 10 in the same class)
to a single split: **0 of 299 clusters span a split**, with the class distribution
kept stratified (all 50 classes in every split; 3–4 test clips per class). It is the
strongest reproducible substitute for signer-disjoint evaluation available from this
metadata. Both protocols are reported everywhere, and the difference between them is
itself a result (see §3).

## 5. Confidence gate (why 0.70 is a starting point, not an optimum)

The gate converts low-confidence outputs into the `UNCERTAIN` state. Sweeping it on
the validation split (`results/threshold_sweep.csv`, `results/threshold_sweep.png`)
measures the coverage/accuracy trade-off; the shipped default was chosen
conservatively *before* this sweep and is deliberately configurable
(`ISL_CONFIDENCE_THRESHOLD`, or per profile within a ±0.2 band).

Proposed model, validation split (152 clips):

| threshold | coverage | selective accuracy | pessimistic accuracy* |
|---|---|---|---|
| 0.50 | 0.803 | 0.8279 | 0.6645 |
| 0.60 | 0.664 | 0.8317 | 0.5526 |
| **0.70 (shipped)** | **0.579** | **0.8523** | **0.4934** |
| 0.75 | 0.539 | 0.8659 | 0.4671 |
| 0.85 | 0.441 | 0.8806 | 0.3882 |
| 0.95 | 0.118 | 1.0000 | 0.1184 |

\* pessimistic accuracy counts every gated-out clip as wrong — i.e. the accuracy if
the user never re-attempts an uncertain sign.

Reading: at 0.70 the system commits to ~58% of validation clips and is right ~85% of the time on
those; lowering to 0.50 raises coverage to ~80% but drops selective accuracy to ~83%;
raising to 0.85 commits to ~44% of clips. **0.70 sits on the conservative side of
the knee and is not claimed to be optimal for any particular user or deployment** —
tune it with this sweep and document your own choice.

```bash
python training/tune_threshold.py            # val split, both protocols
```

## 6. Robustness (real models, perturbed real test tensors)

Accuracy under each perturbation (14 conditions × 3 models; full table in
`results/robustness_results.csv`, plots in `results/robustness_degradation.png`).

Primary protocol (`session_disjoint`, 154 clips):

| condition | LSTM | GRU | **GRU+MHA** | Δ (proposed) |
|---|---|---|---|---|
| clean | 0.6623 | 0.6299 | **0.7727** | — |
| landmark dropout 10% | 0.6753 | 0.6429 | **0.7532** | −0.0195 |
| landmark dropout 30% | 0.5844 | 0.5584 | **0.7208** | −0.0519 |
| left hand removed | 0.2273 | 0.2208 | **0.5325** | −0.2403 |
| right hand removed | 0.1753 | 0.1364 | **0.2597** | −0.5130 |
| both hands removed | 0.0390 | 0.0649 | **0.1169** | −0.6558 |
| Gaussian jitter σ=0.10 | 0.6883 | 0.6299 | **0.7662** | −0.0065 |
| Gaussian jitter σ=0.25 | 0.6818 | 0.5844 | **0.7338** | −0.0390 |
| Gaussian jitter σ=0.50 | 0.5844 | 0.5130 | **0.6818** | −0.0909 |
| frame drop 20% | 0.6494 | 0.6234 | **0.7338** | −0.0390 |
| frame drop 40% | 0.6429 | 0.5844 | **0.7468** | −0.0260 |
| frame drop 60% | 0.5584 | 0.5260 | **0.6883** | −0.0844 |
| uniform 2× subsampling | 0.6688 | 0.6364 | **0.7532** | −0.0195 |
| presence mask zeroed | 0.6623 | 0.6299 | **0.7727** | 0.0000 (coordinate-only input) |

Findings:

1. **Hands carry the signal.** Removing both hands collapses accuracy to 0.03–0.12
   for every model; removing one hand costs 0.31–0.53. The proposed model degrades
   least (left hand −0.31 vs −0.47 LSTM / −0.47 GRU). Practical consequence: the
   hand-detection rate of the extractor, not the network, is the main risk in
   deployment.
2. **Temporal perturbations are tolerated in this test**: dropping 40% of frames costs
   the proposed model about 0.026 accuracy; 60% costs about 0.084.
3. **Coordinate noise is tolerated up to σ≈0.25 shoulder-widths**; at σ=0.5 it still
   beats both baselines.
4. `mask_missing` is a no-op because this build trains with `MASK_ENABLED=False`
   (coordinates only). The condition is kept so the experiment is meaningful when the
   mask build is enabled.
5. In the *pessimistic* sense the gate helps: under `both_hands_missing` 142 of 154
   clips fall below the 0.70 gate for the proposed model, so a live user would see
   `UNCERTAIN` rather than a confidently wrong sign in most cases. That is the
   intended behaviour of the confidence-aware design.

The current results bundle does not include the robustness experiment on the official
split; do not infer its ranking from the session-disjoint table.

```bash
python training/robustness.py --protocol session_disjoint
python training/robustness.py --protocol official
```

## 8. What is *not* measured

Stated plainly so that the numbers above are not over-read:

* **No live-camera accuracy study.** Every accuracy figure comes from INCLUDE
  keypoints. A webcam introduces different frame rates, compression, lighting,
  camera geometry and detector behaviour. The geometry calibration
  (`X_AXIS_SCALE`, see `docs/dataset_audit.md`) aligns the two coordinate systems,
  but live accuracy was not measured and may differ.
* **No unseen-signer or dialect study.** INCLUDE publishes no signer ids, so
  signer-generalisation cannot be quantified here.
* **No continuous-stream or sentence-level evaluation.** The system recognises
  isolated signs; segmentation into sentences/grammar was not attempted.
* **No user study** of the override/personalisation workflow; the audit log and the
  error-review UI make such a study possible, they do not constitute one.
* **No claim that 0.70 is optimal**, that the 30-frame window is optimal, or that a
  particular augmentation setting is best — only that all three models were treated
  identically and that the sweeps are reproducible.
